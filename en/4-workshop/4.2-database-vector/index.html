Data Layer & Vector Database Deployment

4.2. Data Layer & Vector Database Deployment

Lab Overview

In an Enterprise Knowledge AI RAG Assistant ecosystem, the data storage tier requires a seamless harmony between Relational Databases for structured operational metadata and Vector Databases for high-dimensional semantic search indices.

Lab 4.2 details the end-to-end setup of a hardened data tier:

  1. Centralized credentials and configuration management using AWS Secrets Manager, eliminating plaintext .env files from compute nodes.
  2. Provisioning an Amazon RDS PostgreSQL instance powered by AWS Graviton (db.t4g.micro) in an isolated Private Subnet with KMS at-rest encryption.
  3. Deploying and tuning the Qdrant Vector Database container runtime for storing dense embeddings generated by the multilingual BAAI/bge-m3 embedding model.

4.2.1. Centralized Secret Management with AWS Secrets Manager

1. Technical Objectives

  • Prevent plaintext exposure of passwords, API keys, and connection strings in code or local .env files.
  • Centralize all production application parameters as secure Key/Value pairs, automatically encrypted at rest with AWS KMS (Key Management Service).
  • Enable the FastAPI RAG Backend to dynamically inject configuration variables at runtime via IAM Role EC2-S3-RAG.

3. Step-by-Step Implementation & Live Evidence

Step 1: Store New Secret in AWS Secrets Manager

  1. Navigate to AWS Secrets Manager Console → Click Store a new secret.
  2. Select Secret type: Other type of secret.
  3. Under Key/value pairs, add the 16 database connection parameters, S3 prefixes, and Bedrock Mantle keys.
  4. Set Secret name: rag/production/credentials.

Figure 4.2.1.1: Complete inventory of all 16 production secret keys and values configured in AWS Secrets Manager (rag/production/credentials)

Step 2: Dynamic Secret Retrieval in Python Backend

In the FastAPI configuration layer (src/backend/core/config.py), secrets are retrieved dynamically using the AWS Python SDK boto3:

import json
import boto3
from botocore.exceptions import ClientError

def load_secrets_from_aws(secret_name="rag/production/credentials", region_name="ap-southeast-1"):
    client = boto3.client("secretsmanager", region_name=region_name)
    try:
        response = client.get_secret_value(SecretId=secret_name)
        if "SecretString" in response:
            return json.loads(response["SecretString"])
    except ClientError as e:
        print(f"Warning: Could not fetch secrets from AWS Secrets Manager: {e}")
        return {}

4.2.2. Amazon RDS PostgreSQL Deployment in Isolated Subnet

1. Technical Objectives

  • Provision an Amazon RDS PostgreSQL (v18.3) instance to ensure ACID compliance for transactional data: user authentication, role-based access control, document metadata, and chat session histories.
  • Position the database within a Private Subnet (project-subnet-private2-ap-southeast-1b), preventing direct inbound access from the public internet.
  • Utilize the AWS Graviton processor (db.t4g.micro), achieving up to 20% cost reduction and 40% higher price-performance over comparable x86 instances.
  • Enable data encryption at rest (KMS Encryption) using the dedicated aws/rds key.

3. Step-by-Step Implementation & Live Evidence

Step 1: Provision RDS Instance via Console

  1. Navigate to Amazon RDS Console → Databases → Click Create database.
  2. Select Standard create → Engine: PostgreSQL (18.3).
  3. Templates: Free tier / Dev/Test.
  4. Settings:
    • DB instance identifier: rag-db.
    • Master username: postgres.
    • Master password: Enter password (synced with Secrets Manager).
  5. Instance class: db.t4g.micro.
  6. Connectivity:
    • VPC: vpc-03228d0b15b9ea7be.
    • Public access: No.
    • Security group: rag-rds-sg.
  7. Additional configuration:
    • Initial database name: rag_db.
    • Enable encryption: Enabled with aws/rds KMS key.
  8. Click Create database.

Figure 4.2.2.1: Configuration dashboard of rag-db verifying PostgreSQL 18.3, db.t4g.micro, and KMS encryption

Step 2: Database Schema Migration

Upon application boot, SQLAlchemy schema migrations (alembic upgrade head) initialize the tables:

  • users: Stores user accounts, hashed credentials, and role assignments.
  • documents: Tracks uploaded files, S3 URIs, and ingestion states (PENDING, PROCESSING, COMPLETED, FAILED).
  • conversations & messages: Maintains session contexts, user queries, and LLM-synthesized responses.

4.2.3. Qdrant Vector Store Container Deployment

1. Technical Objectives

  • Deploy a specialized Qdrant Vector Database engine optimized for approximate nearest neighbor (ANN) vector search.
  • Index high-dimensional dense embeddings (1024 dimensions) produced by the multilingual BAAI/bge-m3 model.
  • Leverage the HNSW (Hierarchical Navigable Small World) graph indexing algorithm with Cosine Similarity, achieving sub-15ms vector retrieval latencies across large document collections.

2. Docker Compose Deployment Specification

The Qdrant service runs as an isolated container on the EC2 host with persistent EBS volume storage:

  qdrant:
    image: qdrant/qdrant:v1.9.0
    container_name: rag_qdrant
    restart: always
    ports:
      - "6333:6333"
      - "6334:6334"
    volumes:
      - ./data/qdrant_storage:/qdrant/storage
    environment:
      - QDRANT__SERVICE__HTTP_PORT=6333
      - QDRANT__SERVICE__GRPC_PORT=6334

3. Vector Collection Initialization & Verification

The RAG pipeline automatically ensures the existence of the enterprise_knowledge collection:

  • Vector Size: 1024 (matches BAAI/bge-m3 output dimensions).
  • Distance Metric: Cosine.
  • On-Disk Payload: True (stores raw text chunks on SSD, conserving memory).

Verify Qdrant health via the REST API endpoint:
